# Windows productization journey and acceptance harness

## Primary persona

The primary installer user operates business-critical n8n automations on
Windows 11. They can identify their n8n instance, workflow, business entity and
authoritative system of record, but they are not expected to know Git, Python,
Node.js, PostgreSQL, Docker commands, SQL or FlowProof's internal credentials.

They need to answer a business question: did the expected invoice/accounting
outcome occur? They are not installing FlowProof to monitor CPU, container
uptime or n8n execution status.

## Current journey from an existing source checkout

The current README path is a developer path, not an installable product path.

| Step | Current action | Friction counted |
| --- | --- | --- |
| 1 | Ensure Docker Desktop/Linux containers and WSL2 work | prerequisite/support intervention outside FlowProof |
| 2 | Copy `.env.example` to `.env` | terminal command + config file |
| 3 | Replace local placeholders for a safe non-disposable use | manual secret generation/edit/handoff |
| 4 | Run `docker compose up --build --detach` | terminal command and Docker knowledge |
| 5 | Wait for services and diagnose Compose failures | unbounded technical interpretation |
| 6 | Run the admin bootstrap command | terminal command + generated login credential transfer |
| 7 | Open the browser and log in | manual URL/credential step |
| 8 | Run the profile-based false-200 demo | terminal command |
| 9 | Interpret entity, incident, approval, compensation and reread | product value is visible only after technical setup |

Minimum measurable baseline after the checkout already exists:

- terminal commands: `4`;
- manually edited configuration files: `1`;
- internal/manual secret handoffs: at least `1`;
- mandatory setup decisions: at least `3` (safe secret values, admin identity,
  demo execution), before any real n8n/provider connection decisions;
- prerequisites installed by the user: Docker Desktop/WSL2;
- bounded plain-language remediation: absent from the primary path.

The production-core runbook is intentionally stricter and therefore even less
suitable as the golden path: it requires Linux/Bash, immutable image refs,
owner-only secret files with exact UIDs/modes, external state/backup paths and
explicit n8n provisioning inputs.

## Target primary journey

1. Download one clearly named Windows asset.
2. Launch it without a source checkout.
3. Accept or change the local data folder.
4. Let FlowProof perform prerequisite checks, provision local secrets/database
   state, run migrations and create the first administrator without exposing
   internal credentials.
5. Open FlowProof from the installed launcher/Start Menu entry.
6. Choose **Safe demo** or **Protect a real workflow**.
7. For Safe demo, run the labelled `TEST_FIXTURE_ONLY` false-200 scenario.
8. See one entity timeline that distinguishes green execution from a missing
   business outcome, then see bounded evidence, human approval, one narrow
   compensation and a passing independent reread.

Target to the first demo outcome:

- one downloaded asset;
- zero terminal commands;
- zero `.env` or secret-file edits;
- zero copying of generated/internal service secrets between tools;
- at most seven mandatory decisions;
- no more than 15 minutes from asset launch to the first verified demo outcome;
- every failure has one plain-language next action.

Entering an owner-supplied n8n API key once into a protected controller field is
a connection value, not an internal-secret handoff. Xero uses only a public
Client ID plus browser PKCE consent; no access token is entered. Copying a token
generated by FlowProof into n8n, a terminal, `.env` or another file is a manual
secret handoff and fails the golden path.

## Implemented candidate.4 path

The unpublished candidate.4 asset implements the local-appliance portion of
that journey. The WPF controller owns prerequisite reporting, install/repair,
Start/Stop/Restart/Open, sanitized diagnostics, backup, Start Menu shortcut and
preserve-by-default uninstall. It generates internal secrets and the first
administrator without exposing those values to the operator.

For an existing n8n instance, the controller accepts two connection values:

1. an owner-created n8n Public API key in a password field; and
2. a FlowProof URL reachable from n8n.

It validates both endpoints, creates or reuses a fixed `n8n-flowproof` service
principal with only `events:write`, `recovery:execute` and `recovery:verify`,
issues the FlowProof credential in memory, stores it as one encrypted n8n Header
Auth credential, renders four workflows with the returned credential ID,
creates all four and publishes the three webhook workflows. It never grants
`recovery:approve`, never stores the supplied n8n API key and never requires the
operator to copy a FlowProof token. Failed provisioning rolls back created
workflows/credential and revokes the created FlowProof credential.

This path passed against a temporary real n8n 2.30.5 instance from the extracted
candidate.4 without checkout runtime: four workflows,
three published, one encrypted credential and two n8n-origin FlowProof timeline
events. That is `LOCAL_REAL_N8N_TEST_FIXTURE_ONLY`, not provider/company-n8n
acceptance and not a fresh-machine usability PASS.

Candidate.4 retains the bounded update action and adds the Xero PKCE/UI path.
The new asset accepts only the explicitly declared candidate.3 source version
on the same Alembic schema, starts the prior appliance if necessary, creates a
database backup plus checksum/metadata sidecars, loads versioned images, reruns
the idempotent migration and waits for readiness. On failure it restores the
previous environment/state and restarts the prior service configuration. A
source-free candidate.3-to-candidate.4 run passed in 247.432 seconds including
an injected missing-image failure that restored candidate.3 READY with its
administrator intact. The clean update preserved the same administrator, and a
same-version repeat was rejected before mutation. Cross-schema update and
automatic database restore remain unsupported.

## Target real observe-only journey

With provider credentials and a known business entity already available, the
mandatory decisions are bounded to:

1. local data folder;
2. Safe demo versus real workflow;
3. n8n base URL/connection profile;
4. invoice/accounting outcome pack;
5. authoritative read-only provider connection;
6. correlation/entity mapping;
7. one bounded test entity/event confirmation.

Recovery writes remain disabled. The target is one independently reread
outcome, deterministic invariant result and bounded evidence within one working
hour, not an unauthorized mutation.

## Metric definitions

- `download_to_running_seconds`: asset launch to a healthy FlowProof UI. It
  includes prerequisite detection and provisioning.
- `running_to_first_demo_outcome_seconds`: healthy first open to the final
  authoritative reread shown for the fixture scenario.
- `mandatory_decision_count`: choices without which the selected path cannot
  continue. Optional autostart, telemetry or theme choices do not count.
- `terminal_command_count`: commands typed by the tester after receiving the
  asset. Any value above zero fails the golden path.
- `manual_secret_handoff_count`: internal/generated secrets copied between UI,
  terminal, files or services. Any value above zero fails the golden path.
- `support_intervention_count`: moments when another person must explain or fix
  the install.
- `install_failure_count`: failed install attempts before the recorded running
  state.

## Clean-machine protocol

Use Windows Sandbox, a disposable Windows 11 VM or another fresh profile. The
tester must not start in a source checkout.

1. Record OS edition/build, architecture, profile type and preinstalled tools.
2. Copy only the candidate asset and independently recorded checksum into the
   environment. Record the exact Git commit/tree used to build it.
3. Start a screen/log timer at asset launch. Do not open a terminal or coach
   the tester with commands.
4. Record prerequisite result, install/provision progress and every decision,
   failure and support intervention.
5. Complete the safe demo and capture the first entity timeline plus final
   verified outcome without customer data.
6. Close/restart the controller or host as required, reopen FlowProof and prove
   that protection state is not confused with UI-window state.
7. Export sanitized diagnostics and verify that credentials, `.env`, database
   files and raw payloads are absent.
8. Create a backup through the product surface and record its bounded artifact.
9. Uninstall with the default preserve-data choice, reinstall and prove the
   retained data behavior.
10. Record residual limitations and one exact blocker/remediation for every
    failed stage.

The machine-readable record is validated against
`quality/productization/windows-install-session.schema.json`. A `PASS` record
requires evidence for every required stage; `NOT_RUN`, `BLOCKED` and `FAIL`
remain honest non-PASS outcomes.

The provided disposable-profile harness automates this protocol on a local
Windows 11 host. Its first elevated attempt on 2026-08-06 was canceled at the
UAC prompt before temporary-user creation. A post-attempt audit found no
matching user, profile or Public staging directory, so the evidence result is
`BLOCKED`, not PASS or FAIL. The exact next input is approval of that single UAC
run or a disposable Windows 11 VM with Docker Desktop.
